# Scenario: a pull request drops `IsOwner` from a DELETE endpoint

This is the case authzlock exists for. A pull request changes one line of a view, the
endpoint that deletes invoices stops checking who owns the invoice, and every signed-in user
can now delete every invoice. The code review shows a one-line diff; authzlock shows that
the endpoint was loosened.

The project used here is the test fixture `tests/fixtures/scenario_loosen`, and
`tests/test_scenario.py` runs every step below on every CI run. The output blocks on this
page are generated by that test: it fails when they no longer match what authzlock prints,
and `pytest tests/test_scenario.py --update-docs` rewrites them.

## The project

One endpoint, `invoices/<int:pk>/`, served by a DRF `RetrieveDestroyAPIView`, so it accepts
GET and DELETE. Access needs a signed-in user (`IsAuthenticated`) who owns the invoice
(the custom class `IsOwner`):

```python
# billing/permissions.py
class IsOwner(BasePermission):
    """Only the owner of an invoice may read or delete it."""

    def has_object_permission(self, request, view, obj):
        return bool(getattr(obj, "owner", None) == request.user)


# billing/views.py
class InvoiceDetailView(generics.RetrieveDestroyAPIView):
    permission_classes = [IsAuthenticated, IsOwner]
```

The committed `authz.lock` records the route as:

```yaml
- path: invoices/<int:pk>/
  name: invoice-detail
  view: billing.views.InvoiceDetailView
  methods:
  - DELETE
  - GET
  actions: {}
  permission_classes:
  - billing.permissions.IsOwner
  - rest_framework.permissions.IsAuthenticated
```

The full file is `tests/fixtures/scenario_loosen/authz.lock.expected`.

## The pull request

The pull request removes `IsOwner` and keeps `IsAuthenticated`:

```diff
 class InvoiceDetailView(generics.RetrieveDestroyAPIView):
-    permission_classes = [IsAuthenticated, IsOwner]
+    permission_classes = [IsAuthenticated]
```

To reproduce it in a copy of the fixture, from the copy's root:

```console
$ sed -i.orig 's/permission_classes = \[IsAuthenticated, IsOwner\]/permission_classes = [IsAuthenticated]/' billing/views.py
```

(`-i.orig` works with both GNU and BSD `sed`; delete `billing/views.py.orig` afterwards.)

## What `authzlock diff` reports

`authzlock diff --base <ref> --format markdown` compares the lockfile committed at the base
ref with a fresh extraction of the changed code. This is the comment the GitHub Action
posts on the pull request (the test runs it with `--base HEAD`, the commit before the
change):

<!-- scenario:start -->
```markdown
<!-- authzlock -->
### authzlock: access-control changes

1 loosened, 0 tightened, 0 added, 0 removed, 0 changed-unknown

| Change | Methods | Path | View | Details |
|---|---|---|---|---|
| loosened | DELETE,GET | `invoices/<int:pk>/` | `billing.views.InvoiceDetailView` | `R2: custom class billing.permissions.IsOwner removed`<br>`permission_classes`: `[billing.permissions.IsOwner, rest_framework.permissions.IsAuthenticated]` → `[rest_framework.permissions.IsAuthenticated]` |

<details><summary>1 custom permission registry change</summary>

| Change | Class | Details |
|---|---|---|
| removed | `billing.permissions.IsOwner` |  |

</details>
```
<!-- scenario:end -->

The row names the route (`DELETE,GET invoices/<int:pk>/`), the view and the label
`loosened`. The reason cites rule R2 from [classification.md](classification.md): a custom
class was removed and what is left is at most `IsAuthenticated`. authzlock cannot know what
`IsOwner` checked, but it knows the remaining list no longer contains it. The collapsed
section records that no route uses `IsOwner` any more, so it leaves the custom permission
registry; registry changes are not counted in the summary line. The summary line
is `1 loosened, 0 tightened, 0 added, 0 removed, 0 changed-unknown`; the exit code is 1,
with the default `--fail-on any` and with `--fail-on loosened`, so the pull request check
fails.

## What `authzlock check` reports

`authzlock check` compares the same extraction with the lockfile in the working tree, which
the pull request has not updated. It exits 1:

<!-- scenario-check:start -->
```text
authz.lock is out of date.
changed:
  DELETE,GET invoices/<int:pk>/ -> billing.views.InvoiceDetailView
    permission_classes: [billing.permissions.IsOwner, rest_framework.permissions.IsAuthenticated] -> [rest_framework.permissions.IsAuthenticated]
custom permissions removed:
  billing.permissions.IsOwner

To fix: run `authzlock update` and commit authz.lock.
```
<!-- scenario-check:end -->

## Accepting the change

If the change is intended, the author runs `authzlock update` and commits `authz.lock` with
the view. The lockfile diff in the pull request then shows the loosening to reviewers.
After that commit, `authzlock check` prints `authz.lock: up to date` and exits 0, and
`authzlock diff --base HEAD` prints `no changes` and exits 0.

## The other directions

- Adding `IsOwner` back (`[IsAuthenticated]` to `[IsAuthenticated, IsOwner]`) is
  `tightened` by rule R4: one more AND term can only restrict access. It does not fail a
  run with `--fail-on loosened`.
- Replacing `IsOwner` with a different custom class, `IsTenantAdmin`, is `changed-unknown`
  by rule R3, never `loosened`: authzlock cannot tell which of two custom classes is
  stricter, so a human has to look.
