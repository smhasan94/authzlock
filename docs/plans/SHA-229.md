## Approach

`classify.py` defines two ranking tables (`BUILTIN_RANK` for the four DRF classes, and
`DJANGO_AUTH_RANK` for none, `login_required`, `permission_required`) and an ordered list of
rule functions R1 to R8, each taking a `RouteChange` and returning `Classification(label,
reason)` or `None`; the first match wins and R8 is the catch-all `changed-unknown`. The
`reason` names the rule, for example "R2: custom class shop.permissions.IsOwner removed".
A set is "ranked" only when every member is a built-in in the table; any composed
expression, `dynamic`, or third-party class makes it unranked. `classify_diff(diff)` wraps
added and removed routes with those labels and classified changes with their rule. A
property-style test enumerates every combination of old and new sets drawn from built-ins,
two custom classes and `dynamic` and asserts that no result with a custom class in the new
set is ever `loosened`, which is the conservative guarantee the brief demands.
`docs/classification.md` holds the rule table with one example each.

Rejected: a scoring model that sums ranks (opaque; the brief asks for explainable labels);
treating authentication class changes as loosened or tightened (no safe ordering; always
`changed-unknown`).

## Risks and unknowns

- Sets mixing built-ins and customs where the built-in part loosens and the custom part
  is unchanged (for example `[IsAdminUser, IsOwner]` to `[IsAuthenticated, IsOwner]`) are
  `changed-unknown` by R8 in the MVP; noted in the docs as a known conservative outcome.
