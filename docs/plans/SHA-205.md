## Approach

`extract/drf.py` imports DRF lazily inside `try/except ImportError` and exposes
`resolve(view_class) -> DrfInfo | None`, returning `None` for non-DRF views or when DRF is
absent. For an `APIView` subclass it looks at the MRO from the class up to but excluding
`APIView`: if any class in that slice defines `get_permissions` in its own `__dict__`, the
field is `dynamic`; else if any defines `permission_classes`, the value is that attribute with
source `view`; else `api_settings.DEFAULT_PERMISSION_CLASSES` with source `settings-default`.
Authentication follows the same rule with `get_authenticators` and
`DEFAULT_AUTHENTICATION_CLASSES`. Classes are rendered as dotted paths, sorted; composed
operands get a placeholder renderer here that SHA-211 replaces. Nothing is instantiated and
no hook is called.

Rejected: instantiating the view and reading `view.get_permissions()` (runs project code
and guesses for dynamic cases, both forbidden); comparing attribute values with the defaults
(cannot distinguish an explicit copy of the default from the default itself).

## Risks and unknowns

- `api_settings` is a lazy object; reading it after `django.setup()` is safe, but it must be
  read once per extraction, not at import time.
- DRF 3.14 (SHA-272 cell) exposes the same attributes; no version branches expected.

## Out of scope

Routers and `@action` (SHA-207); docstrings and composed expressions (SHA-211).
