## Approach

Expansion happens at classification time, never in the lockfile. `effective.py` exposes
`expand(permission_classes, methods) -> dict[str, tuple[str, ...]]`: for each method it
copies the set, replacing `IsAuthenticatedOrReadOnly` with `AllowAny` on GET and
`IsAuthenticated` otherwise, and `DjangoModelPermissionsOrAnonReadOnly` with `AllowAny` on
GET and `DjangoModelPermissions` otherwise; `AllowAny` is then dropped from any set with
more than one member because it restricts nothing in an AND list. Safe methods are the
DRF triple (GET, HEAD, OPTIONS), hardcoded so classification works without DRF installed.
`classify.py` gains rule R9 ahead of the built-in ranking rule. It applies when
`permission_classes` is the changed field (`permission_source` may change with it),
`methods` is not `any`, and at least one side contains an expandable class. It builds one
synthetic `RouteChange` per method with the expanded sets and classifies it with R1 to R8,
so custom, third-party and composed classes and `dynamic` stay opaque, and
`DjangoModelPermissions`, which is unranked, takes the custom-class rules. The route label
is the worst method label in the order `loosened`, `changed-unknown`, `tightened`, then the
new label `equivalent` when no method's effective rule changed (`IsAuthenticated` to
`IsAuthenticatedOrReadOnly` on a POST-only action, `AllowAny` to
`IsAuthenticatedOrReadOnly` on a read-only ViewSet). The reason names the deciding method,
for example "R9: POST rest_framework.permissions.DjangoModelPermissions ->
rest_framework.permissions.IsAuthenticated". `equivalent` gets a sixth summary count, a
`render_text` group and a row in the collapsed markdown details; `--fail-on loosened` is
unaffected and `scripts/ci/assert_summary.py` accepts the longer line.

Rejected: per-method entries in the lockfile (schema version 2, every lockfile regenerated,
golden files changed, for data that is derivable); reporting the equivalent case as
`changed-unknown` (the tool knows, and the label would be read as a warning); expanding
`DjangoModelPermissions` into its per-method model permissions (needs the model, out of
scope for a classification-time rule).

## Risks and unknowns

- R1 to R8 take a `RouteChange`; the synthetic per-method change is built with
  `dataclasses.replace` on both routes, so `Route` must stay a plain frozen dataclass.
- The summary line format changes, so `assert_summary.py` and its test ship in the same PR
  as `render.py` or the action e2e workflow goes red.
- `DjangoModelPermissions` is only "at least authenticated" here; its per-method model
  permission map is not modelled, which the heuristics page states.

## Out of scope

`DjangoObjectPermissions`; user-defined `OrReadOnly` classes; per-method lockfile entries
(a schema version 2 ticket if reviewers ask for it). No follow-up tickets needed.
