## Approach

Router-generated patterns are ordinary `URLPattern`s whose callback comes from
`ViewSet.as_view(actions, **initkwargs)`; the callback exposes `cls`, `actions` and
`initkwargs`. View identity is `callback.cls` (SHA-200 already prefers `view_class`; add
`cls` as a second lookup). For `@action` routes DRF passes the action's `kwargs` as
`initkwargs`, so a `permission_classes` key there wins with source `action`; otherwise the
ViewSet class resolves through SHA-205. `drf-nested-routers` produces plain patterns with a
parent lookup in the path, so nothing special is needed beyond a fixture proving it. The
`DefaultRouter` api-root is recorded as a normal route.

Rejected: reading `router.registry` directly (misses manually added patterns and duplicates
the URL walk); expanding `@action` methods from `detail`/`url_path` ourselves (DRF already
did it in the pattern).

## Risks and unknowns

- Router lookup regex in paths (`^invoices/(?P<pk>[^/.]+)/$`) is long but deterministic;
  T4 matches on substrings, not the whole string.
- `drf-nested-routers` support for DRF 3.14 through 3.18: verify at install in the
  SHA-272 cell.

## Out of scope

Format-suffix patterns; Django decorators on ViewSets. No follow-up tickets needed.
