Implementation plan

Ticket: SHA-234 Action end-to-end test on the fixture scenario. Written 2026-09-30, updated
2026-10-01 to match the implementation notes on the ticket (report at
`steps.<id>.outputs.report-path`, `base-ref` required in temp repositories). AC3 already
takes a `pr_number` input, so no amendment is needed. Builds on SHA-232 and SHA-231.

## Approach

A second workflow, `.github/workflows/action-e2e.yml`, separate from `ci.yml` so the SHA-184
guards stay untouched; its jobs are independent (no `needs:`), like `ci.yml`'s.
`scripts/ci/prepare_scenario.py DEST [--loosen]` copies `scenario_loosen` to a new git
repository under `$RUNNER_TEMP`, commits it with the golden lockfile as `authz.lock`, and
with `--loosen` applies the one-line edit without committing it. Every job installs Django
5.2 and DRF on Python 3.12 and runs the local action (`uses: ./`) with
`python-version: ""`, `working-directory` pointing at the temp repo and `base-ref: HEAD`
(the temp repo has no `origin`).

- `loosened`: loosened scenario, `fail-on-loosened: false`, `comment: false`;
  `scripts/ci/assert_summary.py` reads `steps.authzlock.outputs.report-path` and asserts the
  summary line is exactly `1 loosened, 0 tightened, 0 added, 0 removed, 0 changed-unknown`
  and the one `loosened` row contains `DELETE` and the view name; it prints the row.
- `clean`: unchanged scenario; asserts a zero summary and "no access-control changes".
- `fails-when-loosened`: loosened scenario with `fail-on-loosened: true` under
  `continue-on-error`; asserts `steps.authzlock.outcome == 'failure'` and that the report
  counts one loosened route.
- `sticky-comment` (`workflow_dispatch` only, input `pr_number`, `pull-requests: write`):
  the action comments only on `pull_request` events, so the job runs it with
  `comment: false` on the clean then the loosened scenario and after each calls the action's
  own `python -m authzlock._github upsert-comment` on `pr_number`, the second body tagged
  with the run id. It asserts the second upsert updated the first one's comment, and
  `scripts/ci/check_sticky_comment.py` asserts the PR has exactly one marker comment with
  the loosened summary and the run id.

Rejected: testing on the repo's own PR (the repo is not a Django project); a nested
checkout of another repo (needs a token and a second repo); a `pr-number` input on the
action (out of scope; changes SHA-232's interface).

## Test mapping

- T1 -> the `loosened` job on this PR.
- T2 -> the `clean` job on this PR.
- T3 -> post-merge: dispatch `sticky-comment` twice with the same `pr_number`; link both
  runs in the ticket.
- T4 -> `tests/test_action_e2e.py::test_t4_summary_parser_accepts_expected_and_rejects_other`.
- T5 -> the `fails-when-loosened` job on this PR.
- Extras in `tests/test_action_e2e.py` run the prepare and assert scripts locally on the
  scenario and check the workflow's jobs, so mistakes fail `pytest` first.

## Risks and unknowns

- `uses: ./` requires the action in the checked-out tree, which it is on PRs from this
  repo; fork PRs are out of scope.
- `sticky-comment` cannot run before merge: `gh workflow run` needs the workflow on the
  default branch.

Marketplace listing; other repos. No follow-up tickets needed.
