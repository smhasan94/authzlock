Implementation plan

Ticket: SHA-209 Django auth decorators and mixins. Written 2026-09-30. Builds on SHA-203.

## Approach

Two sources of truth, runtime first, AST second. Runtime: the `__wrapped__` chain and
`inspect.getclosurevars` find `login_required` and `permission_required` wrappers by the
closure variables Django uses (`test_func`, `perm`), which is enough to set the booleans
but not to read permission strings reliably or to tell `login_required` from a custom
`user_passes_test`. AST: `extract/source.py` gets the source of the function or class
(`inspect.getsource` after `inspect.unwrap`), parses it, and reads `decorator_list`: names
`login_required`, `permission_required(<literal or list of literals>)`, `user_passes_test`,
`method_decorator(login_required, name="dispatch")`; anything else lands in
`unknown_decorators`, and a non-literal `permission_required` argument is recorded as
`permission_required(<non-literal>)` rather than guessed. Mixins come from the MRO:
`LoginRequiredMixin`, `PermissionRequiredMixin` (reading the `permission_required`
attribute, string or list), `UserPassesTestMixin`. When source is unavailable the runtime
result stands and `unknown_decorators` is empty.

Rejected: evaluating `test_func` (executes project code); regex over source text (AST is
exact and handles multi-line decorators).

## Risks and unknowns

- `inspect.getsource` on a class returns the whole class; decorators are on the
  `ClassDef`, fine. For a function defined inside another function it can fail; fall back
  to runtime.
- Django 5.1's `LoginRequiredMiddleware` changes the meaning of "no decorator" project-wide;
  out of scope, noted for a Later ticket if users ask.

## Out of scope

DRF views; evaluating test callables. No follow-up tickets needed.
