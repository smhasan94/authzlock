## Approach

One document, two encodings. `render.py` gains `to_document(classified, base_info,
locations) -> dict` with fixed key order: `schema_version` (1), `tool` (`name`, `version`),
`base` (`ref`, `lockfile`, `lockfile_found`), `summary` (the five counts of the markdown
summary line, `changed_unknown` with an underscore), `changes` and `custom_permissions`
(`added`, `removed`, `changed` from the registry diff). Each change has `label`, `rule`
(`R2`, or `null` for added and removed), `reason`, `route` (`key`, `path`, `methods`,
`view`), `fields` as `[{field, old, new}]` carrying lockfile values unchanged so `dynamic`,
`null` and composed expressions pass through, and `location` as `{file, line}`.
`render_json` is `json.dumps(indent=2, ensure_ascii=False)` plus a newline.
`sarif.py::render_sarif` maps that document onto SARIF 2.1.0: one run, driver `authzlock`
with version and homepage, five `rules` named by label, one result per change with
`ruleId` equal to the label, `level` (`loosened` error, `changed-unknown` and `added`
warning, `tightened` and `removed` note), `message.text` equal to the text renderer's line
plus the reason, one physical location (`%SRCROOT%`-relative `uri`, `startLine`) and
`partialFingerprints["authzlock/routeKey"]` so code scanning keeps one alert per route
across pushes. Registry-only changes are not results. A missing base lockfile is
`lockfile_found: false` and a `toolExecutionNotifications` note. Locations are resolved at
diff time and never stored in the lockfile: `locate.py` imports the module part of the
`view` dotted path, walks the attribute chain, unwraps, and uses `inspect.getsourcefile`
and `getsourcelines`; paths are relative to `gitutil`'s repo root with forward slashes,
and anything unimportable, outside the repo or without source (removed routes included)
falls back to the lockfile path at line 1, so no result lacks a location. `cli.py` extends
`--format` to `text|markdown|json|sarif`; exit codes, `--fail-on` and stderr error text
are unchanged, so stdout is one complete document or empty. `docs/diff-json.md` documents
every key beside a JSON Schema at `docs/diff.schema.json`; `docs/cli.md` gains a code
scanning snippet (`diff --base origin/main --format sarif > authzlock.sarif`, then
`github/codeql-action/upload-sarif@v3`).

Rejected: source locations in the lockfile (line numbers churn on every edit and change
the schema); SARIF alone (verbose; the JSON document is what it is built from); vendoring
the SARIF JSON Schema for tests (large; the structural subset GitHub requires is checked
by hand and one real upload is recorded on the PR); an `--output` flag (redirection is
enough and matches the other formats).

## Risks and unknowns

- CBVs reach the diff as a dotted class path, function views as a function path; both
  resolve through `inspect`. Views built with `exec` or inside functions fall back to the
  lockfile location, which is honest but less useful.
- Code scanning marks alerts fixed when results disappear; after a merge the next diff is
  empty, so alerts close on their own. The docs say the SARIF describes a PR, not a state.
- `tool.version` changes per release, so tests compare it with `__version__` rather than
  using golden files.
