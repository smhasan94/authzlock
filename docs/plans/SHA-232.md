## Approach

`action.yml` at the repo root is a composite action with inputs `settings-module`
(required), `lockfile` (default `authz.lock`), `python-version` (default `3.12`),
`fail-on-loosened` (default `true`), `comment` (default `true`) and `working-directory`
(default `.`). Steps: set up Python, `pip install "${{ github.action_path }}"`, fetch the PR
base ref with depth 1, run `authzlock diff --base origin/<base> --format markdown` capturing
stdout to a file and the exit code without failing the step, then run
`python -m authzlock._github upsert-comment` which uses `gh api` with `github.token` to find
the newest issue comment containing `<!-- authzlock -->` and update it, or create one; an
empty diff posts "no access-control changes". A final step fails the job when
`fail-on-loosened` is true and the summary line reports a non-zero loosened count. All
comment logic lives in `src/authzlock/_github.py` so it is unit-testable with a fake `gh`
on `PATH` that records calls and returns canned JSON. `docs/github-action.md` has the
copy-paste workflow with `permissions: pull-requests: write, contents: read`.

Rejected: a Docker action (slow, and users already have Python); a JavaScript action
(another toolchain); posting a new comment per push (noisy threads).

## Risks and unknowns

- The composite action runs in the target repo's job, where Django and the project must
  be importable; the docs make the caller install the project first.
- `gh` is preinstalled on GitHub-hosted runners; self-hosted runners without it are out of
  scope and documented.
