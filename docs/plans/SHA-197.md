## Approach

`authzlock.django_loader.load_project(settings_module)` sets `DJANGO_SETTINGS_MODULE` when
an argument is given, otherwise requires the variable, then calls `django.setup()` once,
guarded by `django.apps.apps.ready`. Every failure becomes `ProjectLoadError` with a plain
two-line message: the missing module name and the words "cannot import", or the hint to set
`DJANGO_SETTINGS_MODULE` or pass `--settings`, or the original exception text for a settings
module that raises. `authzlock.extract.extract()` is a stub returning an empty `Inventory`
(schema_version 1, no routes) so the harness has something to run. `authzlock._dump` is a
tiny `__main__` that loads the project, extracts and prints `Inventory.to_dict()` as JSON.
The test harness `tests/harness.py::run_extract(fixture, *, block_modules=())` runs
`python -m authzlock._dump` in a subprocess with `PYTHONPATH` and `DJANGO_SETTINGS_MODULE`
set; `block_modules` injects `sys.modules[name] = None` before import so later tickets can
simulate a missing dependency such as DRF without a separate environment.

Rejected: in-process fixture switching with `importlib.reload` (Django cannot be set up
twice); a `manage.py` per fixture (unneeded; `call_command("check")` covers AC6).

## Changes

- `src/authzlock/errors.py`, `django_loader.py`, `model.py` (minimal `Inventory`),
  `extract/__init__.py` (stub), `_dump.py`.
- `tests/harness.py`; `tests/conftest.py` re-exports `run_extract` as a fixture.
- `tests/fixtures/function_views/` (`settings.py`, `urls.py`, app `shop` with `public`,
  `members_only` under `login_required`, `staff_report` under `permission_required`);
  `tests/fixtures/minimal/` (one view, used to prove isolation); `tests/fixtures/broken/`
  (`settings.py` raising `RuntimeError("boom")` at import).
- `tests/test_django_loader.py`.

## Test mapping

- T1 -> `test_t1_load_project_reads_env_var` (subprocess, prints `apps.ready`).
- T2 -> `test_t2_explicit_settings_argument_wins` (env set to a bogus module).
- T3 -> `test_t3_missing_module_raises_project_load_error` (in-process; fails before setup).
- T4 -> `test_t4_no_settings_anywhere_gives_hint` (in-process, env cleared).
- T5 -> `test_t5_two_fixtures_extract_in_one_session` (`function_views` twice and `minimal`).
- T6 -> `test_t6_fixture_passes_django_check` (subprocess `call_command("check")`).
- T7 -> `test_t7_settings_import_error_is_reported` (subprocess on the `broken` fixture,
  expects `boom` in stderr and exit 2).
- Extra: `test_extra_dump_outputs_schema_version` (harness returns `schema_version == 1`).

## Sequence

1. errors, loader, model skeleton, stub extract, `_dump`; in-process tests T3, T4.
2. Fixture projects; harness; T1, T2, T5, T6, T7, extra. `nox` green across the matrix.

## Risks and unknowns

- Fixture settings need a `DATABASES` entry for `check` to pass; use in-memory SQLite.
- Subprocess start-up cost is about half a second per call; fine at this scale.

## Out of scope

Walking URLs (SHA-200); any DRF fixture (SHA-205). No follow-up tickets needed.
