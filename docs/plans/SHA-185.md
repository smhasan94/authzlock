Implementation plan

Ticket: SHA-185 Release tooling to PyPI. Written 2026-09-30. Assumes the AC1 and AC3
precondition amendment proposed alongside this plan is approved. Builds on the CI workflow
from SHA-184.

## Approach

One workflow, `.github/workflows/release.yml`, with two triggers. A push of a tag matching
`v*` builds the sdist and wheel, checks that the tag equals the built version, and publishes
to PyPI with `pypa/gh-action-pypi-publish@release/v1` under `permissions: id-token: write`
(trusted publishing, no stored token). A `workflow_dispatch` with inputs `target`
(`testpypi`, default, or `pypi`) and an optional `tag` runs the same build and version check
and publishes to the chosen index; the `tag` input exists so the mismatch path can be
exercised without pushing a real tag. Publishing steps run in GitHub environments `pypi`
and `testpypi`, which is where the trusted publishers are bound. `CHANGELOG.md` follows Keep
a Changelog with an Unreleased section; `docs/releasing.md` lists the exact steps and the
one-time PyPI setup.

Rejected: API tokens in secrets (the brief wants no credentials; trusted publishing is the
standard now); `hatch-vcs` for versions (SHA-181 decided on a literal `__version__`);
automatic changelog generation (out of scope).

## Changes

- `.github/workflows/release.yml`: jobs `build` (build, version check, upload `dist/` as an
  artifact) and `publish` (`needs: build`, downloads the artifact, publishes to the index
  chosen by trigger and input). The version check reads the wheel filename and compares with
  the tag or `tag` input, failing with both values in the message.
- `CHANGELOG.md`: header, Unreleased section with the work so far.
- `docs/releasing.md`: one-time trusted publisher setup on PyPI and TestPyPI, then the
  steps update changelog, bump `__version__`, PR, tag, push, verify install.
- `tests/test_release_workflow.py`: static checks on `release.yml`, CHANGELOG and docs.
- The SHA-184 test `test_extra_jobs_are_independent` covers `ci.yml` only; `release.yml`
  legitimately uses `needs`.

## Test mapping

- T1 -> manual dispatch to TestPyPI on a `0.0.1.devN` version; run URL and the
  `pip install -i https://test.pypi.org/simple/ authzlock==0.0.1.devN` output recorded.
- T2 -> manual dispatch with `tag: v9.9.9` on the PR branch; expected failure at the
  version check step with both versions in the log; run URL recorded.
- T3 -> `tests/test_release_workflow.py::test_t3_publish_uses_trusted_publishing` (publish
  step uses `pypa/gh-action-pypi-publish`, job has `id-token: write`, no `password` input).
- T4 -> `tests/test_release_workflow.py::test_t4_changelog_and_releasing_docs`
  (`## [Unreleased]` present; each documented step name present in `docs/releasing.md`).
- T5 -> `tests/test_release_workflow.py::test_t5_release_triggers_only_on_version_tags`
  (`push.tags == ["v*"]`, no `push.branches`).
- Extra: `test_extra_no_secrets_referenced` (no `secrets.` anywhere in `release.yml`).

## Sequence

1. Write `release.yml`, `CHANGELOG.md`, `docs/releasing.md`; static tests green; `nox` green.
2. Owner configures the TestPyPI trusted publisher for repo, workflow `release.yml`,
   environment `testpypi` (and the PyPI one for later).
3. Dispatch to TestPyPI (T1), then dispatch with a mismatched `tag` (T2); record URLs.
4. PR, review, merge.

## Risks and unknowns

- Trusted publishers must exist before T1 can pass; this is a manual step only the repo
  owner can do. The plan makes it a stated precondition.
- TestPyPI refuses re-uploads of the same version, so each dry run needs a new `devN`.
- `pypa/gh-action-pypi-publish` requires the artifact layout `dist/`; the build job uploads
  exactly that.

## Out of scope

The 0.1.0 release (SHA-237); signing; changelog automation. No follow-up tickets needed.
