Implementation plan

Ticket: SHA-237 Release 0.1.0 to PyPI. Written 2026-09-30. Builds on SHA-236 and SHA-185.
Precondition: the PyPI trusted publisher for `release.yml` and environment `pypi` exists.

## Approach

Follow `docs/releasing.md` exactly. One PR moves the Unreleased changelog entries under
`## [0.1.0] - <date>`, bumps `__version__` to `0.1.0` and adds the post-release verification
workflow job. After merge, tag `v0.1.0` on the merge commit and push it; the release
workflow publishes. Then move the `v1` tag to the same commit and push it with `--force`
(documented as the one intended force push), create the GitHub release with the changelog
section as notes, and dispatch `post-release-verify.yml`, which installs
`authzlock==0.1.0` from PyPI on Python 3.10 and 3.13, prints the version and runs the README
quickstart test against the installed package. Records of every run URL go on the ticket.

Rejected: tagging before the changelog PR merges (tag and version must agree; SHA-185's
check enforces it); making `v1` a branch (an action ref is conventionally a moving tag).

## Changes

- `CHANGELOG.md`, `src/authzlock/__init__.py`,
  `.github/workflows/post-release-verify.yml` (`workflow_dispatch` with `version` input).
- `tests/test_release_workflow.py`: T5 extension and the `v1` check script under
  `scripts/ci/check_v1_tag.sh`.

## Test mapping

- T1 -> release workflow run for `v0.1.0`; URL and PyPI page recorded.
- T2 -> `post-release-verify` run; URL recorded.
- T3 -> same run, quickstart job.
- T4 -> `scripts/ci/check_v1_tag.sh` run in the verify workflow (`git rev-parse v1` equals
  `v0.1.0`).
- T5 -> `tests/test_release_workflow.py::test_t5_changelog_010_section_complete`.
- T6 -> a second push of `v0.1.0` from a different commit on a throwaway clone is refused
  by GitHub (tag exists) or by PyPI (version exists); the refusal text is recorded and
  `docs/releasing.md` documents it.

## Sequence

1. Changelog and version PR with the verify workflow; merge.
2. Tag, publish, `v1`, GitHub release.
3. Verify workflow; record; ticket to review.

## Risks and unknowns

- The trusted publisher setup is manual; nothing here works without it.
- The `v1` tag will move on every later 1.x release; note that in `docs/releasing.md`.

## Out of scope

Announcements; code changes (new tickets). No follow-up tickets needed.
