Ticket: SHA-243 Later: FastAPI extraction. Written 2026-09-30. Assumes the acceptance
criteria, T-cases and dependencies proposed alongside this plan are approved (the ticket is
a Later placeholder with both sections still to be written). Builds on SHA-200, SHA-205,
SHA-211, SHA-225 and SHA-229.

## Approach

FastAPI is a second extractor behind the same `Inventory`, lockfile and CLI; the schema stays
at version 1 and no route field is added. `fastapi_loader.py::load_app(import_string)`
mirrors `django_loader`: it parses `module:attr` (attr defaults to `app`), imports the
module, checks the object is a Starlette application and turns every failure (`fastapi` not
installed, module not importable, attribute missing or not an app) into a two-line
`ProjectLoadError`. `extract/fastapi.py::extract_app(app) -> Inventory` walks `app.routes`
recursively, following `Mount` with its prefix (router prefixes are already merged by
`include_router`). Each HTTP route gives one `Route`: `path` as reported, `name`, `view`
through SHA-200's `view_identity()`, `methods` sorted upper-case without HEAD and OPTIONS;
a `WebSocketRoute` is recorded with `methods: ["WEBSOCKET"]` rather than dropped. Access
rules come from `fastapi.dependencies.utils.get_flat_dependant(route.dependant)`, the same
flattening FastAPI uses for its OpenAPI security section: every dependency callable
(route-level, router-level, parameter `Depends` and `Security`, nested ones flattened,
class dependencies by class path) lands in `permission_classes` as a dotted path, with
`Security` scopes appended as `path[scope_a,scope_b]`; security scheme instances
(`fastapi.security.*`) land in `authentication_classes` as their class path. Both sources
are the string `dependency`; `django_auth`, `object_scoping` and `actions` stay null or
empty. Nothing is called. SHA-211's registry is reused with the filter "module not under
`fastapi` or `starlette`", so every dependency gets a `custom_permissions` entry.

`cli.py` adds `--framework {auto,django,fastapi}` and `--app MODULE:ATTR` (also
`AUTHZLOCK_APP`) to `update`, `check` and `diff`. `auto` picks fastapi when `--app` or
`AUTHZLOCK_APP` is set, django when `--settings` or `DJANGO_SETTINGS_MODULE` is set, and
exits 2 with a hint when both or neither are set; `_dump` applies the same rule from the
environment, so the harness only gains a `framework="fastapi"` argument. `classify.py`
gains rule R10 (R9 is SHA-239's per-method rule) for routes whose `permission_source` is `dependency`: `permission_classes`
changes are always `changed-unknown` (a removed dependency may be `get_db`; ranking it would
raise false `loosened` alarms), `authentication_classes` going from non-empty to empty is
`loosened`, empty to non-empty is `tightened`, anything else `changed-unknown`.

Rejected: a `dependencies` route field or a top-level `framework` key (schema bump for no
reader benefit; `permission_source: dependency` already says what the list means); reading
`app.openapi()` or a `TestClient` (runs project code, and OpenAPI omits dependencies without
security schemes); recording `app.dependency_overrides` (test-time; documented as ignored).

## Risks and unknowns

- `get_flat_dependant` and `Dependant.security_requirements` are internal API; a unit test
  pins the attribute names so a FastAPI release that renames them fails loudly. The pin
  `fastapi>=0.100` covers the Pydantic v2 line; older releases are not tested.
- `include_router` copies router dependencies onto each route, so one dependency can appear
  twice in the tree; the list is deduplicated before sorting. Lambda dependencies render as
  `module.<lambda>`: deterministic but uninformative, noted in the heuristics page.
- Importing the app module executes project code at import time, as assumption A2 already
  allows for Django.

## Out of scope

Starlette-only applications; middleware-based auth (`AuthenticationMiddleware`); ranking
dependencies by name. Follow-up: an `app` key in `[tool.authzlock]` once SHA-238 lands.

## Addendum (2026-10-04)

Five tickets merged after this plan was written. Changes they force, proposed on the ticket
as AC amendments:

- SHA-238 (`[tool.authzlock]`): `config.py` gains an `app` key next to `settings`. Option
  resolution goes tier by tier: flags (`--app`, `--settings`), then environment
  (`AUTHZLOCK_APP`, `DJANGO_SETTINGS_MODULE`), then config (`app`, `settings`). `auto` uses
  the first tier that sets either; both set in that tier exits 2 with the hint. So a shell
  that exports `DJANGO_SETTINGS_MODULE` does not break `--app`. A load failure for an `app`
  taken from config gets the same "set in [tool.authzlock] in <path>" line as `settings`.
  The deferred "app key" follow-up moves into this ticket.
- SHA-244 (`gen-tests`): the generated tests use Django's test client, so a FastAPI lockfile
  would otherwise skip every route with a misleading "not a built-in DRF permission"
  reason. `gen-tests` exits 2 with "gen-tests supports Django lockfiles only" when any
  route has `permission_source: dependency`. A FastAPI `TestClient` generator is out of
  scope.
- SHA-239 (R9): R10 goes first in `RULES`, ahead of R9 and R1 to R8, so a dependency route
  never reaches R4 ("custom added", which would say `tightened`). The T8 test is named
  `test_t8_r10_table_and_dependency_sets_never_ranked`.
- SHA-241 (`diff --format json|sarif`) and SHA-245 (ignore list): no code change expected,
  because endpoints have dotted paths that `locate.py` resolves and the ignore matchers use
  `path` and `view`. New T12 adds one test for each on `fastapi_basic`.
